# 폴리마켓 자연어 배팅 검색

> 이 문서는 계획서다. 항목이 끝나면 지우고, 다 끝나면 파일째 지운다.
> 완료 기록은 git 이력이 맡는다.
>
> `services/web/docs/polymarket-dashboard.md`(현재 스냅숏 대시보드)를 **전제로** 한다.
> 그 문서가 먼저 지워져도 이 계획은 남아야 해서 파일을 나눴다.

## 1. 무엇을 만드나

지금 탐색기의 검색(`/api/forecast/events?q=`)은 **제목·태그에 그 글자열이 그대로
들어 있는지**만 본다(`services/web/polymarket/repository.py`의 `events`). event 제목은
영어이고 질문은 한국어라, "트럼프 관세가 한국에 미칠 영향" 같은 질문은 사실상
0건이다.

여기에 **한국어 자연어 질문으로 관련 배팅을 찾는 검색**을 얹는다. 핵심 원칙 하나로
요약된다.

> **무거운 일은 순회 때 미리 하고, 검색하는 순간에는 LLM을 부르지 않는다.**

event마다 LLM이 한국어 요약·검색 키워드를 **미리** 달아 두고, 검색은 그
메타데이터 위에서 파이썬만으로 한다. 그래야 공개 웹의 두 규칙 — 요청을 받아 밖으로
나가는 경로를 만들지 않는다, 링크를 받은 사람 수만큼 Neurons가 나가지 않는다 —
을 그대로 지킨다(`code_guide.md` "공개 웹은 봇과 다른 프로세스이고 `GET`만 가진다").

검색 결과의 **순서**를 LLM으로 다듬는 재정렬은 따로 두지 않는다. 로그인 계정의 자연어 질문에 답하는
질의응답(`polymarket-consensus-qa.md`)이 1차 후보 중에서 고르는 것이 그 일을 겸한다.

## 2. 전체 흐름

```text
refresh (4시간)            ─ current.json 교체
  └ OnSuccess
     annotate (신규)        ─ 새로 생겼거나 제목이 바뀐 event만 LLM 주석
                              → data/webpub/polymarket/search_index.json
공개 웹 (요청 시)
  repository.events(q=…)   ─ 질문 토큰 × (키워드·제목·요약·태그) 점수 + 거래량
                              LLM 호출 없음
```

## 3. 주석 one-shot

독립 one-shot `services/web/polymarket/annotate.py`. `sector_brief`·`trending`과 같은
자리다. `infra/systemd/stock-chatbot-polymarket-refresh.service`의 `OnSuccess=`에
`stock-chatbot-polymarket-annotate.service`를 더한다. timer는 늘리지 않는다.

**왜 refresh 안에 넣지 않나**: sector brief와 같은 이유다. LLM 실패가 generation
승격을 막으면 Cloudflare가 죽은 날 확률 숫자까지 멈춘다.

### 3-1. event마다 받는 것

| 필드 | 예 ("Will the Fed cut rates in December?") | 쓰임 |
|---|---|---|
| `summary_ko` | 연준이 12월 회의에서 기준금리를 내릴지 | 목록 표시, 검색 |
| `keywords` 5~10개 | 연준, 미국 금리, 금리 인하, FOMC, 파월, 통화정책 | **검색의 핵심** |
| `subtopic` | 미국 통화정책 | 분류 보강 |

- **요약만으로는 부족하다.** 검색 시점에는 LLM이 없으므로 질문 낱말과 메타데이터
  낱말이 맞물려야 찾힌다. 요약 한 줄에 우연히 같은 낱말이 들어 있기를 기대하면
  빠지는 게 많다. 그래서 한국어·영어 표기와 동의어를 키워드로 따로 받는다.
- **대분류는 새로 만들지 않는다.** `taxonomy.classify`의 12개 분류·태그·지역이 이미
  있다. `subtopic`은 그 아래 한 단계만 더한다.
- **요약에 확률 숫자를 넣지 않는다.** 확률은 4시간마다 바뀌고, 모델이 방향을
  뒤집어 쓴 전례가 있다(`title_probability` docstring). 요약은 "무엇에 거는
  배팅인가"만 담는다. **그래야 한 번 만든 주석을 event가 닫힐 때까지 재사용할 수
  있고, 이것이 비용을 낮추는 핵심이다.**

### 3-2. 대상과 캐시

- 캐시 키는 `event id + 제목 해시`다. **새로 생겼거나 제목이 바뀐 event만** 호출한다.
- `current.json`에 없는 id(닫힌 event)는 색인에서 지운다. 과거 조회는 만들지 않는다.
- **거래량(`volume24hr`) 내림차순으로 처리한다.** 백필이 여러 날 걸리므로 사람들이
  실제로 찾는 event가 먼저 검색되게 한다.
- 입력은 제목·태그와 description 앞 300자다. description은 detail에만 있으므로
  **처리할 event만** `read_detail`로 seek한다(전량을 읽지 않는다).

### 3-3. 호출과 응답 계약

- 한 호출에 25건을 묶는다(`POLYMARKET_ANNOTATE_BATCH_SIZE`). 시스템 프롬프트를 건마다
  되풀이하지 않기 위해서다. 더 묶으면 `max_tokens` 절단 한 번에 버리는 건수가 커진다.
  한 실행은 최대 8배치다 — 백필이 하루 예산을 첫 주기에 몰아 쓰지 않게 한다.
- 응답 형식은 스키마로 강제한다(`response_format`). 시장상황 보고서에서 추가 비용 0으로
  실측된 방식이다. `CLOUDFLARE_MODEL`을 바꾸면 JSON 모드 스모크를 다시 돌린다.
- 모델은 **입력 번호로만** event를 가리킨다. id를 받아 적게 하지 않는다(리서치
  evidence와 같은 규칙).
- 파서는 번호 범위·중복·필수 필드를 엄격히 검사한다. `finish_reason=length`는 실패다
  — 그 배치는 버리고 다음 주기에 다시 시도한다(같은 실행 안에서 재시도하지 않는다).
- 누락된 번호는 주석 없음으로 남고 다음 주기 대상이 된다.

### 3-4. 예산

refresh가 CPU·요청 예산을 스스로 지키는 것과 같은 방식이다.

- `POLYMARKET_ANNOTATE_MAX_DAILY_NEURONS`(초기 4,000)를 넘으면 그 실행을 멈춘다
  (`last_result: "skipped_budget"`, 종료 코드 0).
- 응답의 `usage`에서 Neurons를 누적한다. 추정이 아니라 실측으로 센다.
- `quota_exhausted`는 재시도하지 않고 실행을 끝낸다.
- **실패한 호출도 센다.** 세지 않으면 반복 실패가 예산을 그대로 통과한다.

## 4. 검색 색인 저장

**`current.json`에 넣지 않는다.** 한글은 UTF-8로 글자당 3바이트라 요약·키워드를
합치면 건당 약 250 B이고, 21,872건이면 **약 5.2 MiB**다. 16 MiB 상한
(`polymarket-dashboard.md` 7-4)의 3분의 1을 먹고, compact에 필드를 더하면 event 수가
곱해진다는 규칙에 정면으로 걸린다.

- 별도 파일 `data/webpub/polymarket/search_index.json`에 둔다. 쓰기는
  `services/web/core/storage.py`의 원자적 쓰기만 쓴다.
- `PolymarketRepository`가 `current.json`과 같은 방식(mtime이 바뀔 때만 교체)으로
  읽는다.
- **웹 프로세스는 `MemoryMax=256M`이다.** 5 MiB 파일이 파이썬 객체로 올라가면 몇 배로
  불어난다. 착수 전에 색인 크기와 로드 후 RSS를 잰다(8절 0단계). 넘치면 키워드를
  정규화된 문자열 하나로 합쳐 객체 수를 줄인다.

## 5. 1차 검색 (LLM 없음)

- **질문 정규화**: casefold, 공백 분리, 한국어 조사·어미 접미사 제거(짧은 고정 목록),
  불용어 제거.
- **필드 가중치**: 키워드(4) > 제목(3) > 세부 주제·요약(2) > 태그(1). 한 낱말은 가장
  무거운 칸 하나로만 센다. 영어 낱말은 단어 앞머리부터 맞추고(입력 중인 "tru"도
  Trump에 닿는다) 두 글자 이하는 단어 전체만 본다("ai"가 "said"에 걸리지 않게).
  한국어는 띄어쓰기가 흔들리므로 공백을 뺀 형태도 본다.
- **남기는 기준**: 질문 낱말의 절반 이상이 맞아야 한다. 전부를 요구하면 긴 질문이
  0건이 되고, 하나만 요구하면 "한국" 하나로 수백 건이 걸린다.
- **정렬**: 맞은 낱말 수 → 칸 가중 점수 → 24시간 거래량. 거래량은 동점을 가를
  때만 쓴다(`services/web/polymarket/relevance.py`).
- 주석이 아직 없는 event도 제목·태그로는 찾힌다. 옛 경로를 살려 두는 것이 아니라
  같은 점수식에서 주석 필드만 비어 있는 것이다.
- **API**: 기존 `q`를 그대로 쓰고, `q`가 있으면 `sort=relevance`를 기본으로 한다.
  카테고리·지역·상태 필터는 지금처럼 함께 건다. ETag는 `generation_id`에 더해 색인
  mtime을 넣는다 — 주석만 바뀐 주기에도 결과가 달라지기 때문이다.
- **화면**: 결과 행에 한국어 요약(`summary`)을 한 줄 붙인다. 모델이 쓴 문자열이므로 `esc()`를
  거친다. 요약은 보조이고 원문 제목과 확률을 항상 함께 보인다.

**이 단계의 한계**: 표현이 전혀 다른 질문("경기침체" ↔ "GDP 마이너스 성장")은 키워드
품질에 달려 있다. "70% 넘는 것만", "이번 달 마감" 같은 조건은 해석하지 않는다 —
기존 필터·정렬이 맡는다.

## 6. 비용

실측식 `neurons ≈ 0.00463×입력 + 0.0304×출력`(`code_guide.md`, 현재 모델 기준)으로
추정한다. **첫 주 뒤 실측으로 이 표를 갱신한다.**

| 항목 | 가정 | 추정 |
|---|---|---|
| 주석 1건 | **실측 ~2.8 Neurons**(2026-09-24 두 실행: 200건 571, 199건 546) | 추정은 3.9였다 |
| 첫 백필 18,992건 | 하루 4,000 상한 → 하루 약 1,400건 | **약 2주**(2026-09-24 기준 371건 완료) |
| 백필 이후 | 하루 신규 event 수 × 2.8 | **미정** — 신규 수를 며칠 더 잰다 |

무료 한도(하루 10,000)는 봇·섹터 브리프와 함께 쓴다. 섹터 브리프가 하루 약
1,500~2,500이다. 백필 동안 상한을 잠시 올릴지는 봇 사용량을 보고 정한다.

## 7. 실패 처리

- 주석 배치 하나가 실패해도 나머지 배치는 쓴다. 실패한 event는 다음 주기 대상이다.
- 전부 실패하면 색인을 다시 쓰지 않는다. 직전 색인이 last-good으로 남는다.
- 색인이 없거나 낡아도 검색은 제목·태그만으로 동작하고, 대시보드의 나머지는 그대로
  뜬다.
- `current.json`이 없으면 조용히 종료한다.

## 8. 단계

주석 one-shot·1차 검색·화면은 구현했다(`annotate.py`·`relevance.py`·`repository.py`,
`infra/systemd/stock-chatbot-polymarket-annotate.service`). 남은 것:

0. **배포 뒤 실측** — 2026-09-24에 잰 것: 건당 ~2.8 Neurons, 버린 행 0.25%(400건 중
   1건), 색인 건당 ~220 B(다 차면 ~4.1 MiB), 웹 RSS 123 MB/256M(색인 2% 상태).
   **남은 것**: 하루 신규 event 수(며칠치 `annotate_status.json` 표본), 색인이 찬 뒤
   웹 RSS, 거래량 상위 200건 주석 품질 눈검사(첫 200건에서 "US-Iran ceasefire
   continues"가 "미국이 이란에 군사 행동을 할지"로 달린 오역 1건을 봤다).

## 9. 판정

- 한국어 질문 30개 평가 세트를 만든다(정치·거시·지정학·크립토·스포츠 고르게).
  질문마다 정답 event를 사람이 고른다.
- 지표: **상위 10건 안의 정답 비율**과 0건 질문 수. 기준선은 지금의 글자열 검색이다.
- 1단계는 기준선보다 확실히 나아야 한다(0건 질문이 대부분 사라져야 한다). 그렇지
  않으면 키워드 프롬프트부터 고친다.
- 30문항 세트와 측정 프로브는 `services/web/tests/polymarket_ask_probe.py`에 있다(질의응답의 상위 30
  기준. 2026-11-04 결과는 `polymarket-consensus-qa.md` 2절).

## 10. 테스트

- 주석 파서: 번호 범위·중복·누락·필수 필드·`truncated` 실패.
- 캐시: 제목이 바뀐 event만 다시 호출되고, 닫힌 event가 색인에서 빠진다.
- 예산: 상한 초과 시 `skipped_budget`, 실패한 호출도 누적된다.
- 검색: 조사 제거, 필드 가중, 주석 없는 event도 제목으로 찾힘, 필터와 결합.
- 모든 LLM 호출은 mock한다.

## 11. 안 하는 것

- **임베딩 검색.** 질문마다 임베딩 호출이 나가고, 벡터를 웹 프로세스(256M)에
  올려야 한다. 1단계의 판정이 나쁠 때만 다시 본다.
- **전량을 LLM으로 판정.** 검색 1회에 21,872건을 묻는 구조는 비용이 맞지 않는다.
- **요약에 확률·가격을 넣는 것.** 3-1절.
- **과거 generation 검색.** 화면은 "지금"만 본다.
- **`current.json`에 주석 필드 추가.** 4절.
